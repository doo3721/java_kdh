## 1교시: 스레드 스케줄링, 컨텍스트 스위칭, 동기화

- 스레드 스케줄링 (Thread Scheduling)
    - 컴퓨터의 CPU 코어 수는 한정되어 있으나 실행해야 할 스레드의 수는 훨씬 많은 것이 일반적
    - 이에 따라, 운영체제(OS)와 JVM의 스레드 스케줄러가 각 스레드에게 CPU 자원을 나누어 주어 공평하게 실행될 수 있도록 순서와 실행 시간을 제어하고 분배하는 작업
    - 자바 스레드는 OS의 스레드 스케줄링 정책(선점형 우선순위 방식 및 라운드 로빈 등)을 바탕으로 관리됨
- 컨텍스트 스위칭 (Context Switching)
    - 멀티 스레드 환경에서 하나의 CPU를 공유하여 어러 작업을 동시에 처리하는 것처럼 보이게 하는 시분할(Time Sharing) 연산 과정에서 발생함
    - 현재 CPU를 할당받아 실행 중이던 스레드의 작업 정보를 임시로 보관하고, 새롭게 실행할 다음 스레드의 이전 보관 정보를 CPU로 로딩하여 교체하는 작업을 뜻함
    - 컨텍스트 스위칭이 발생할 때마다 CPU 레이스터 데이터를 저장하고 복원하는 오버헤드(시간 소모)가 누적됨
- 스케줄링/스위칭과 동기화의 상관관계
    - 자바 소스코드 상에서 balance -= amount 라는 코드는 단 한 줄의 명령처럼 보이지만, 실제 기계어 수준에서는 다음과 같이 다단계 세부 명령어로 쪼개어져 실행됨
        - 현재 메모리 잔액 값을 CPU로 읽어오기 (Load)
        - 차감 연산 수행하기 (Sub)
        - 연산된 결과 값을 다시 메모리에 덮어쓰기 (Store)
    - 초기 잔액이 10,000원인 계좌에서 스레드 A와 B가 동시에 7,000원씩 출금을 시도할 때
        - 스레드 A가 1단계(Load)를 수행하여 메모리에서 10,000원을 읽어 자신의 레지스터에 보관함
        - 스레드 A가 2단계(Sub)를 수행하여 레지스터 내부 연산으로 결과 값 3,000원(10,000 - 7,000)을 도출함
        - [컨텍스트 스위칭 발생] 스레드 A가 결과 값을 메모리에 기록(3단계 Store)하기 직전에 멈추고 스레드 B가 실행권을 넘겨받음
        - 스레드 B가 1단계(Load)를 수행함. 아직 스레드 A가 결과를 저장하지 않았으므로 메모리 잔액은 여전히 10,000원으로 읽힘
        - 스레드 B가 2단계(Sub) 및 3단계(Store)를 끝까지 수행하여 결과 값 3,000원을 메모리에 최종 저장함 (메모리 잔액 = 3,000원)
        - 스레드 A가 다시 CPU를 할당받아 멈췄던 지점인 3단계(Store)부터 시작함. 스레드 A는 자신이 이전에 연산해 둔 결과 값 3,000원을 메모리에 덮어씀 (메모리 잔액 = 3,000원)
        - 결과적으로 총 14,000원의 출금이 연이어 접수되었음에도 최종 잔액은 3,000원만 남게 되어 데이터 정합성이 깨지는 경쟁 상태(Race Condition)가 유발됨
    - 따라서 이러한 순서 교체 환경 속에서 여러 단계의 기계어 연산들이 도중에 끊기지 않고 하나의 묶음(원자성)으로 완전히 종료될 수 있도록 해주는 안전장치인 동기화(Synchronization)의 활용이 필수적으로 요구됨

## 2교시: 스레드 동기화, synchronized

- 스레드 동기화
    - 동기화의 필요성
        - 여러 스레드가 동시에 공유 자원에 접근하여 쓰기 처리를 진행할 때 데이터의 정합성이 깨지는 경쟁 상태(Race Condition)가 나타나 데이터 불일치가 발생하는 걸 막기 위해서 필요
    - synchronized 키워드
        - 특정 객체나 메소드에 락(Lock)을 설정하여, 오직 키를 얻는 유일한 스레드만 임계 영역(Critical Section) 내부 코드를 통과할 수 있도록 강제적으로 제한하는 키워드

        ```java
        class Account {
            private int balance = 10000;
        
            // synchronized 키워드로 임계 영역을 설정하여 두 스레드가 동시에 출금하지 못하도록 차단함
            public synchronized boolean withdraw(int amount) {
                if (balance >= amount) {
                    balance -= amount;
                    return true;
                }
                return false; // 잔액 부족
            }
        }
        ```

- 스레드 안전성 확보
    - 스레드 안전성(Thread Safely)
        - 여러 스레드가 동시에 접근하여 작업을 수행하더라도 문제없이 항상 예측 가능한 정상 데이터를 도출하는 성질
    - 안전성 확보 전략
        - 무상태성 설계: 상태를 저장하는 클래스의 멤버 변수(필드)를 최대한 배제하고 내부 지역 변수만을 활용하여 동시성 마찰을 사전 회피
        - 불변성(Immutable) 활용: 한 번 선언되면 절대 수정 불가능한 객체(final 지시어 등 활용)를 공유하여 스레드가 상태 변경 자체를 하지 못하도록 차단
        - 스레드 안전 컬렉션 적용: Vector나 Hashtable과 같이 모든 동작에 락이 걸려 성능이 저하되는 구조 대신, CopyOnWriteArrayList나 ConcurrentHashMap 등 정교하게 튜닝된 락 구조를 갖춘 컬렉션을 활용

## 3교시: 가상 스레드

- 가상 스레드
    - 가상 스레드 도입 배경
        - 기존 자바의 전통적인 플랫폼 스레드(Platform Thread)는 OS 스레드를 1:1로 매핑함
        - 이 방식은 생성 및 컨텍스트 스위칭 비용이 매우 크며, 동시 요청 처리를 위해 많은 수의 스레드를 생성하면 메모리 고갈 문제를 야기함
        - 자바 21부터 정식 도입된 가상 스레드는 OS 스레드에 종속되지 않고 JVM이 자체적으로 관리하는 경량 스레드
        - 적은 리소스로 수백만 개의 동시 실행 흐름을 지원함
    - 플랫폼 스레드와 가상 스레드 비교
        - 플랫폼 스레드
            - OS 스레드와 1:1 대응하며 크기가 큼 (약 1MB 스택 할당)
            - 생성 비용이 비쌈
            - 주로 스레드 풀을 통해 재사용함
        - 가상 스레드
            - OS 물리 스레드와 M:N 대응(수많은 가상 스레드가 소수의 실제 OS 스레드에 번갈아 얹혀 동작)하며 크기가 극도로 작음 (수 KB 범위)
            - 생성 비용이 매우 저렴함
            - 풀링하지 않고 필요할 때마다 생성하고 폐기함
    - 동작 원리
        - 가상 스레드가 실행될 때, JVM이 관리하는 플랫폼 스레드인 캐리어 스레드(Carrier Thread)에 배정되어 실행됨
        - 실행 중 데이터베이스 조회나 파일 읽기 등의 대기 작업(블로킹 I/O)을 만나 멈추게 되면, 가상 스레드는 캐리어 스레드로부터 즉시 분리됨
        - 이 때, 가상 스레드의 작업 상태 정보는 힙 메모리 영역에 임시 저장되고, 캐리어 스레드는 대기하지 않고 다른 가상 스레드를 실행하는 데 투입됨
        - 대기 작업이 끝나면 가상 스레드는 힙에 저장해 두었던 상태를 복구하여 기용한 캐리어 스레드에 다시 배정되어 작업을 이어서 수행함
        - 핵심 요약
            - 가상 스레드를 사용하면 실제 물리 OS 스레드는 OS 레벨에서 무겁게 멈추거나 컨텍스트 스위칭을 겪지 않고 계속 가동 상태를 유지하며 동작함
            - 대신 JVM이 가상 스레드들의 작업 상태 정보를 자체 힙 메모리에 객체로 저장하고 복원하면서 컨텍스트 스위칭을 흉내 내어 구현하기 때문에 오버헤드가 적고 빠른 속도를 보장
    - 사용 예시

        ```java
        // 1. 단일 가상 스레드 직접 생성 및 실행
        Thread virtualThread = Thread.ofVirtual().start(new Runnable() {
            @Override
            public void run() {
                System.out.println("가상 스레드 실행: " + Thread.currentThread());
            }
        });
        
        // 2. 가상 스레드 전용 Executor 사용 (Task당 스레드 생성 방식)
        // var: 지역 변수 타입 추론 (컴파일러가 우변의 대입 값인 ExecutorService 타입을 자동으로 유추함)
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            executor.submit(new Runnable() {
                @Override
                public void run() {
                    System.out.println("Executor 기반 가상 스레드 실행");
                }
            });
        } // executor가 자동으로 close 되면서 모든 가상 스레드가 종료될 때까지 대기
        ```


## 4교시: 람다식

- 람다식 (Lambda Expression)
    - 익명 함수를 표시하기 위해 리턴 타입을 메소드 명을 제거하고 화살표 기호 ->를 사용하여 구현하는 문법 규칙

    ```java
    // 람다식(익명 함수)
    (int a, int b) -> {
      return a + b;
    }
    
    or
    
    // 단일 실행 명령문일 경우 중괄호 `{}`와 return 키워드, `;` 생략 가능
    (int a, int b) -> a + b
    ```

    - 람다식의 동작 원리
        - 람다식은 독립적인 함수가 아니라, 하나의 추상 메소드만 가진 함수형 인터페이스의 익명 구현 객체로 만들어짐
        - 컴파일 시점에 JVM이 동적으로 클래스 구현체를 생성하므로, 매번 새로운 익명 클래스 파일(.class)을 물리적으로 생성하여 사용하는 방식에 비해 메모리 효율성과 실행 속도가 개선

        ```java
        // 단 하나의 추상 메서드만 가지는 인터페이스 정의 (함수형 인터페이스)
        interface Calculator {
          int add(int a, int b);
        }
        
        public class LambdaTest {
          public static void main(String[] args) {
            // 1. 람다식 미사용 (전통적인 익명 클래스 구현 방식)
            Calculator classic = new Calculator() {
              @Override
              public int add(int a, int b) {
                return a + b;
              }
            };
            System.out.println(classic.add(5, 3)); // 8
        
            // 2. 람다식 사용
            Calculator lambda = (a, b) -> a + b;
            System.out.println(lambda.add(5, 3)); // 8
          }
        }
        ```

    - 람다식의 이점
        - 코드 간결화 및 가독성 증가: 클래스 정의와 메소드 오버라이딩 선언부 등의 무의미한 보일러플레이트 코드를 생략하여 핵심 로직만 명확히 표기
        - 메소드의 매개변수로 전달 가능: 람다식 자체를 다른 메소드의 인자(파라미터)로 전달할 수 있어, 동작 자체를 하나의 값처럼 자유롭게 취급하고 유연하게 실행할 수  있음
        - 메모리 효율성 개선: 매번 불필요한 익명 구현 클래스 파일(.class)을 무겁게 생성하여 메모리에 로드하지 않기 때문에, 메모리 낭비를 줄이고 프로그램 실행 효율성을 높임
    - 람다 캡처링과 로컬 변수 제약 사항
        - 람다식 내부에서 외부 범위에 속한 메소드 내 지역 변수를 참조할 때, 해당 변수는 명시적으로 final 상수로 선언되어 있거나 대입 연산이 추가 발생하지 않는 사실상 final(effectively final) 상태에 도달해 있어야 사용 가능
        - 지역 변수는 스택(Stack) 메모리 영역에 생성되므로 스레드가 종료되면 소멸되는데, 람다의 생명 주기는 다를 수 있어 자바 런타임이 해당 지역 변수를 복사(Copy)하여 독립적으로 저장해서 사용
        - 복사된 데이터와 원본의 일관성을 유지하기 위해 변경이 불가한 final 제약을 준수하도록 강제 설계됨

## 5교시: 표준 함수형 인터페이스

- 표준 함수형 인터페이스
    - 함수형 프로그래밍을 돕기 위해 자바 표준 라이브러리 패키지인 java.util.function 내부에서 미리 범용 프로토타입으로 제안한 인터페이스 계층
    - Stream API를 통한 컬렉션 데이터 정제 및 변환에 주로 사용
    - 핵심 표준 어댑터 비교

        | **분류** | **매개변수 종류** | **반환 값 형식** | **주요 가동 메서드 명칭** | **핵심 목표** |
        | --- | --- | --- | --- | --- |
        | Predicate | T (단일 객체) | boolean | test(T t) | 입력된 객체의 유효성 검사 및 통과 필터링 |
        | Consumer | T (단일 객체) | 없음 (void) | accept(T t) | 입력값을 소모하여 가공 결과를 화면 출력 등 처리 |
        | Function | T (변환 타겟) | R (변환 완료) | apply(T t) | 입력 데이터를 특정 포맷이나 다른 유형으로 매핑 |
        | Supplier | 없음 | T (신규 생성) | get() | 지연 로딩 방식을 통한 신규 데이터 조달 및 리턴 |
        
        ```java
        // 표준 함수형 인터페이스 응용 문법
        Predicate<Integer> checkLimit = num -> num > 100;
        System.out.println("제한 초과 판단: " + checkLimit.test(150));
        
        Consumer<String> writeLog = msg -> System.out.println("로그 누적: " + msg);
        writeLog.accept("이벤트 발생");
        ```


## 6교시: 메소드 참조, 어노테이션

- 메소드 참조 (Method Reference)
    - 람다식이 메소드를 정의하지 않고 다른 클래스의 메소드를 매개변수 그대로 호출할 때, 코드 중복을 정리하여 간결하게 압축 표기하는 기법
    - 문법
        - `타겟_클래스_혹은_인스턴스::메서드명`
    - 참조 형식 구분
        - 정적 메서드 참조: `Class::staticMethod`
            - 예: `(s) -> Integer.parseInt(s)` 대신 `Integer::parseInt`
        - 임의 객체의 인스턴스 메서드 참조: `Class::instanceMethod`
            - 예: `(s) -> s.length()` 대신 `String::length`
        - 특정 객체의 인스턴스 메서드 참조: `instance::instanceMethod`
            - 예: `(s) -> System.out.println(s)` 대신 `System.out::println`
        - 생성자 호출 참조: `Class::new`
            - 예: `() -> new ArrayList<>()` 대신 `ArrayList::new`

        ```java
        // 람다 기본 형태
        Function<String, Integer> lambda = s -> Integer.parseInt(s);
        
        // 메서드 참조 기법으로 축소 구현
        Function<String, Integer> ref = Integer::parseInt;
        ```

- 어노테이션 (Annotation)
    - 프로그램 소스코드 안에 다른 프로그램을 위한 메타데이터를 삽입하는 특수 주석 문법
    - 일반 주석과의 차이점
        - 일반 주석: 개발자가 가독성을 위해 작성하여 컴파일 시 완전히 제거
        - 어노테이션: 컴파일러나 JVM이 프로그램 가동 및 빌드 과정에서 읽어 들이고 해석하여 특별한 기능 처리를 수행할 수 있도록 지원함
    - 주요 용도 분류
        - 컴파일러용 힌트 제공: 자바 컴파일러가 코드를 컴파일할 때 문법적 오류나 잠재적 결함을 검증할 수 있게 지원함
        - 빌드 시점의 정보 가공: 빌드 툴이나 동적 코드 생성 엔진이 컴파일 단계에서 새로운 파일이나 코드를 생성하도록 메타데이터를 공급함
        - 런타임 제어 정보 주입: 애플리케이션이 실행되는 중에 특정 값을 바탕으로 객체를 생성하거나 특정한 비즈니스 로직의 분기를 제어할 수 있도록 동적으로 가공 정보를 제공함
- 자바 표준 어노테이션과 메타 어노테이션
    - 주요 표준 어노테이션 (자바 내장 어노테이션)
        - @Override: 해당 메소드가 부모 타입의 추상 메소드나 인터페이스 명세를 올바르게 오버라이딩했는지 컴파일러에게 지시하여 검증을 유도함
        - @Deprecated: 더 이상 보존이나 보안상 권장하지 않고 차후 삭제될 가능성이 높은 기능을 선언, 적용 지점을 개발자가 호출하면 경고를 출력하도록 유도함
        - @SuppressWarnings: 컴파일러가 유발하는 유효성이나 타입 경고를 특정 영역 내에서 의도적으로 무시하도록 제어함
        - @FunctionalInterface: 단 하나의 추상 메소드만을 보유한 유효한 함수형 인터페이스 규격인지 검증하며, 규정을 위반할 경우 컴파일 에러를 차단함
    - 메타 어노테이션 (어노테이션 정의를 위한 어노테이션)
        - 어노테이션을 설계할 때, 해당 어노테이션이 어디에 적용되고 언제까지 유지될지 속성을 제어하기 위해 선언부에 지정하는 어노테이션
        - @Target: 어노테이션을 클래스, 메소드, 필드, 매개변수 중 어느 지점에 기입할 수 있는지 유효 범위를 확정함
        - @Retention: 어노테이션 정보의 보존 생명 주기를 지정함
            - RetentionPolicy.SOURCE: 컴파일 시점에만 컴파일러 검증용으로 유지되고, 빌드 이후 .class 파일이 생성될 때 소멸함
            - RetentionPolicy.CLASS: 컴파일된 클래스 파일 내부까지는 메타데이터로 영구 수록되나, JVM 런타임에 클래스 로더가 메모리에 클래스를 로드할 때는 버려져 실행 시점에는 조회할 수 없음
            - RetentionPolicy.RUNTIME: 실행 시점까지 메모리에 정보가 보존되므로, JVM 기동 중 리플렉션 기술을 통해 동적으로 정보를 파싱하여 연동 코드를 가동할 수 있음
        - @Documented: API 문서 생성 시 해당 어노테이션 정보가 자동으로 명세되도록 제어함
        - @Inherited: 어노테이션이 부모 클래스에 붙었을 때 자식 클래스에게도 어노테이션의 유효 속성이 그대로 상속되도록 설정함
