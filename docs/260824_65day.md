## 4. 데이터 지속성 통제 (Bind Mounts VS Named Volumes)

- 컨테이너 내부 쓰기 레이어는 컨테이너 정지 및 삭제 시 데이터가 소멸되므로, 영구 보존이 필요한 데이터를 위해 데이터 지속성(Data Persistence) 메커니즘을 사용함
- 컨테이너 구동 후 애플리케이션이 실행되면서 생성되는 파일들을 호스트의 파일 시스템에 보관해서 컨테이너가 삭제 되더라도 파일이 유지되도록 하는 목적

### 4.1 Named Volumes

**1) Named Volumes 작동 원리 및 특징**

- Docker 데몬이 직접 관리하는 전용 영역(`/var/lib/docker/volumes/`)에 독립된 데이터 볼륨을 생성하고 컨테이너와 연동하는 방식
- 호스트의 디렉토리 구조에 의존하지 않으며 복수 컨테이너 간 데이터 공유 및 데이터베이스 파일 영구 보존에 적합함
- OS별 실제 저장 위치 및 호스트 접근 특징
    - Linux 호스트: 호스트 파일 시스템의 `/var/lib/docker/volumes/[볼륨명]/_data` 경로에 직접 저장됨.
    - Windows (Docker Desktop): WSL 2 가상 머신 내부 영역에 저장되며, 윈도우 탐색기 주소창에 `\\wsl$` 입력 후 `docker-desktop -> mnt -> docker-desktop-disk -> data -> docker -> volumes -> [볼륨명] -> _data` 순으로 이동해서 물리 데이터를 확인할 수 있음.
    - macOS (Docker Desktop): 경량 Linux 가상 머신(VM) 내부의 `/var/lib/docker/volumes/[볼륨명]/_data` 경로에 저장되며, macOS 호스트 상에서는 가상 디스크 파일(`Docker.raw`) 내부에 저장되므로 Finder에 직접 노출되지 않고 가상 머신 디버그 쉘을 통해 접근함.

**2) 볼륨 관리 CLI 명령어 (`docker volume`)**

```bash
# 1. DB 데이터 전용 볼륨 및 게시판 첨부파일 전용 볼륨 생성
docker volume create spring-board-db-data

# 2. DB 컨테이너에 Named Volume 마운트 구동(mysql은 기본으로 var/lib/mysql 폴더에 데이터를 저장함)
docker run -d --name db-server --network myapp-net -p 3306:3306 -v spring-board-db-data:/var/lib/mysql -e MYSQL_DATABASE=board_db -e MYSQL_ROOT_PASSWORD=root mysql:9.7

# 3. Spring Board 컨테이너에 Named Volume 마운트 구동
docker run -d --name spring-board --network myapp-net -p 80:8080 -v spring-board-file-uploads:/app/uploads {dockerhub-username}/spring-board:1.0

# 4. 볼륨 목록 조회 및 상세 정보 확인
docker volume ls
docker volume inspect spring-board-file-uploads

# 5. 개별 볼륨 삭제 및 미사용 찌꺼기 볼륨 일괄 강제 정리
docker volume rm spring-board-file-uploads
docker volume prune -f
```

- `docker volueme create [볼륨명]`: 독립된 데이터 볼륨을 새로 생성함
- `docker volume ls`: 호스트 내에 생성된 볼륨 목록을 조회함
- `docker volume inspect [볼륨명]`: 특정 볼륨을 상세 저장 경로 및 정보를 확인함
- `docker volume rm [볼륨명]`: 사용하지 않는 볼륨을 삭제함
- `docker volume prune [옵션]`: 현재 어떤 컨테이너에도 연결되어 있지 않은 고립된 찌꺼기 익명 볼륨 및 미사용 볼륨을 일괄 정리함.
    - `f` (`-force`): 별도의 삭제 승인 확인 절차 없이 즉시 강제로 정리함.

### 4.2 Bind Mounts

**1) Bind Mounts 작동 원리 및 특징**

- 호스트 파일 시스템의 특정 절대 경로(Absolute Path)를 컨테이너 내부 디렉토리 경로와 1대1로 직접 마운트하여 공유하는 메커니즘
- 호스트의 외부 설정 파일 (application.yml)이나 로그, 첨부 파일 디렉토리를 이미지를 재빌드하지 않고 컨테이너 내부 환경에 실시간으로 반영 및 보존함
- 로컬 개발 환경에서 Hot Reloding, 웹 정적 리소스 테스트, 외부 설정 파일 주입 시 유용함

**2) Bind Mounts 기본 문법 및 사용법**

- 기본 형식: `v "[호스트_절대경로]:[컨테이너_내부경로]"` (예: `v "${PWD}/uploads:/app/uploads"`)
- 읽기 전용 보안 옵션: 컨테이너 내부에서 수정이 불가능하도록 설정 시 끝에 `:ro` 지정 (예: `v "${PWD}/config/app.properties:/app/config/app.properties:ro"`)

**3) PWD(Print Working Directory / Present Working Directory) 환경 변수 활용**

- 현재 터미널 쉘 세션이 위치한 작업 디렉터리의 절대 경로를 동적으로 반환함
- Docker 바인드 마운트 옵션(`-v`)은 호스트 디렉터리 지정 시 상대 경로(예: `./uploads`)를 지원하지 않고 절대 경로를 요구하므로 `${PWD}` 환경 변수를 조합하여 사용함
- Windows Git Bash 환경의 `${PWD}` 경로 변환 충돌 및 해결책
    - MSYS2 경로 자동 변환 충돌 원인: Windows Git Bash의 `${PWD}`가 반환하는 리눅스 스타일 절대 경로(`/c/...`)를 MSYS2 런타임이 Windows 경로 포맷(`C:\...`)으로 강제 자동 변환하는 과정에서, 마운트 옵션의 콜론(`:`) 및 컨테이너 내부 경로와 결합되어 구문 오류가 발생함.
    - `MSYS_NO_PATHCONV=1` 환경 변수의 역할: MSYS2 런타임의 인자 자동 경로 변환 기능을 비활성화(Disable)하여 `${PWD}`가 반환하는 리눅스 스타일 경로(`/c/...`)를 원본 그대로 `docker` CLI 프로세스로 전달함. (Windows용 Docker CLI 엔진은 `/c/...` 형태의 호스트 드라이브 경로를 Windows 파일 시스템 경로로 자체 인식하므로 바인드 마운트가 정상 수행됨).
    - 컨테이너 내부에서 사용할 실제 리눅스 경로를 표현하는 명령어 바로 앞에 `MSYS_NO_PATHCONV=1`을 붙여 구동.
- Linux 환경 예시

```bash
# 1. 호스트 디렉터리 생성 및 설정 파일 준비
mkdir -p ./config ./logs ./uploads
echo "server.port=8080" > ./config/application-prod.yml

# 2. 읽기 전용 보안 옵션(:ro)과 함께 바인드 마운트 구동
docker run -d --name spring-board-app -p 8080:8080 \
  -v $(pwd)/config/application-prod.yml:/app/config/application-prod.yml:ro \
  -v $(pwd)/logs:/app/logs \
  -v $(pwd)/uploads:/app/uploads \
  spring-board:1.0
```

- Windows + Git Bash 예시

```bash
# 1. 호스트 시스템에 첨부파일 저장용(uploads) 및 로그 저장용(logs) 디렉터리 생성(프로젝트 루트에서 실행)
mkdir uploads logs

# 2. 업로드 및 로그 디렉터리 바인드 마운트 구동 (MSYS_NO_PATHCONV=1 환경 변수 적용)
MSYS_NO_PATHCONV=1 docker run -d --name spring-board-4 --network board-net -p 81:8080 \
  -v "${PWD}/uploads:/app/uploads" \
  -v "${PWD}/logs:/app/logs" \
  {dockerhub-username}/spring-board:1.0
```

# **Spring Board 컨테이너 배포 및 구동 실습**

- 실행할 모든 명령은 spring-board 프로젝트 docs 폴더 아래에 docker-single.sh 파일에 저장한 후 IntelliJ의 spring-board 프로젝트 터미널에서 실행.
- {dockerhub-username}는 모두 본인의 도커허브 계정명으로 수정.

## **1. 실습 인프라 리소스 구성 목록**

- 사용자 정의 브릿지 네트워크: `board-net` (데이터베이스와 애플리케이션 컨테이너 간의 독립 서브넷 통신망)
- DB 전용 Named Volume: `board-db-data` (MySQL 데이터베이스 파일 영속성 보존)
- 게시판 파일 및 로그 Bind Mounts 디렉터리: `uploads` 및 `logs` (호스트 파일 시스템 직접 연동 및 영속성 보존)
- DB 컨테이너: `board-db` (MySQL 9.7 기반 백엔드 데이터베이스 서버)
- 애플리케이션 컨테이너: `board-app` (Spring Boot 기반 게시판 웹 애플리케이션)

## **2. 기존 실습 리소스 조회 및 전체 삭제**

- 실습 환경을 깨끗하게 초기화하기 위해 기존의 모든 컨테이너, 이미지, 네트워크 및 Named Volumes 목록을 먼저 확인한 후 전부 일괄 삭제함.
- 명령어 문법
    - 서브셸 구문(`$(명령어)`): 괄호 내부 명령어의 실행 결과(예: 전체 컨테이너/이미지/볼륨 ID 목록, -q 옵션을 지정할 경우 ID만 조회)를 외부 명령어의 인자로 동적으로 전달함.
    - 표준 오류 리다이렉션(`2>/dev/null`): 삭제할 리소스 대상이 없어 발생하는 에러 메시지(표준 오류 2번)를 화면에 띄우지 않고 소멸시킴.
    - 예외 보장 구문(`|| true`): 앞선 삭제 명령어가 에러(Exit Code 1)로 종료되더라도 스크립트 실행이 중단되지 않고 다음 명령어로 정상 진행되도록 보장함.

```bash
# Spring Board 컨테이너 배포 및 구동

# 1. 기존 컨테이너, 이미지, 네트워크, 볼륨 목록 사전 조회
docker ps -a
docker images
docker network ls
docker volume ls

# 2. 모든 기존 컨테이너 강제 중지 및 전체 삭제
docker rm -f $(docker ps -aq) 2>/dev/null || true

# 3. 모든 기존 이미지 강제 전체 삭제
docker rmi -f $(docker images -q) 2>/dev/null || true

# 4. 모든 기존 Named Volumes 및 미사용 네트워크 전체 삭제
docker volume rm -f $(docker volume ls -q) 2>/dev/null || true
docker network rm -f $(docker network ls -q) 2>/dev/null || true
```

## **3. 인프라 리소스 선언 (네트워크, Named Volume 생성 및 Bind Mounts 사전 준비)**

- 독립된 서브넷 통신망 형성을 위해 `board-net` 전용 브릿지 네트워크를 생성하고, 데이터 영속성 보존을 위해 `board-db-data` 볼륨 선언 및 `uploads`, `logs` 디렉터리를 사전 생성함.

```bash
# 5. Spring Board 애플리케이션 전용 사용자 정의 네트워크 생성
docker network create board-net

# 6. DB 데이터 영속성 보존용 Named Volume 생성
docker volume create board-db-data

# 7. 게시판 첨부파일(uploads) 및 시스템 로그(logs) 바인드 마운트 전용 호스트 디렉터리 사전 생성
mkdir -p uploads logs
```

## **4. MySQL 데이터베이스 컨테이너 구동 (Named Volume 마운트)**

- 백엔드 데이터 저장소인 MySQL 9.7 컨테이너를 생성하여 `board-net` 네트워크에 연결하고 `board-db-data` 볼륨을 마운트함.

```bash
# 8. MySQL DB 컨테이너 백그라운드 구동, 볼륨 마운트 및 환경 변수 설정
docker run -d --name board-db \

  -p 3306:3306 \
  -v board-db-data:/var/lib/mysql \
  -e MYSQL_DATABASE=board_db \
  -e MYSQL_USER=board-app \
  -e MYSQL_PASSWORD=Board123! \
  -e MYSQL_ROOT_PASSWORD=rootpass \
  mysql:9.7
```

## **5. Spring Board 이미지 빌드 및 Docker Hub 배포**

- Dockerfile을 작성하고 `docker build` 명령어를 활용하여 Spring Boot 애플리케이션 이미지를 생성한 후 다중 태깅(Semantic Versioning)을 적용하여 Docker Hub 레지스트리에 배포함.
- 프로젝트 루트에 Dockerfile 작성

    ```docker
    FROM eclipse-temurin:25-jre
    WORKDIR /app
    COPY build/libs/*.jar spring-board.jar
    ENTRYPOINT ["java", "-jar", "spring-board.jar"]
    ```

```bash
# 9. Gradle 프로젝트 빌드 (단일 실행용 JAR 파일 생성)
./gradlew clean bootJar
```

## **6. Spring Board 애플리케이션 컨테이너 배포 (Bind Mounts 연동)**

- Docker Hub 원격 레지스트리 정상 배포 여부를 명확히 테스트하기 위해 로컬에 빌드되어 남아있는 이미지를 먼저 삭제(`docker rmi`)함.
- 로컬 이미지가 삭제된 상태에서 `docker run`을 실행하면, Docker 데몬이 호스트에서 이미지를 찾지 못하고(`Unable to find image locally`) Docker Hub 원격 레지스트리로부터 이미지를 자동으로 다운로드(pull)하여 배포함.

```bash
# 13. Docker Hub 원격 레지스트리 다운로드 연동 테스트를 위해 로컬 빌드 이미지 완전 삭제
docker rmi {dockerhub-username}/spring-board:1.0.0 {dockerhub-username}/spring-board:1.0 {dockerhub-username}/spring-board:1 {dockerhub-username}/spring-board:latest

# 14. Docker Hub에서 원격 이미지를 자동 다운로드(pull)하여 Spring Board 애플리케이션 컨테이너 배포, Bind Mounts 및 포트 바인딩(80:8080)
MSYS_NO_PATHCONV=1 docker run -d --name board-app \
  --network board-net \
  -p 80:8080 \
  -v "${PWD}/uploads:/app/uploads" \
  -v "${PWD}/logs:/app/logs" \
  -e SPRING_DATASOURCE_URL="jdbc:mysql://board-db:3306/board_db?useSSL=false&allowPublicKeyRetrieval=true" \
  -e SPRING_DATASOURCE_USERNAME=board-app \
  -e SPRING_DATASOURCE_PASSWORD=Board123! \
  -e SPRING_SQL_INIT_MODE=always \
  {dockerhub-username}/spring-board:1.0
```

## **8. 웹브라우저 테스트 및 Bind Mounts 연동 검증**

- 웹 브라우저를 통해 배포된 Spring Board 애플리케이션에 접속하여 기능이 정상 동작하는지 테스트하고, 호스트 디렉터리와의 바인드 마운트 연동 상태를 확인.

### **8.1 웹 브라우저 접속 및 게시글 목록 조회 검증**

- 웹 브라우저 주소창에 `http://localhost` 접속하여 게시판 메인 페이지 및 게시글 목록 화면이 정상적으로 출력되는지 확인.

### **8.2 로그인 및 파일 첨부 게시글 등록 검증**

- 회원 로그인을 진행한 후 신규 게시글 작성 화면에서 첨부파일(이미지 파일 등)을 등록하고 게시글 생성.

### **8.3 호스트 디렉터리(uploads, logs) Bind Mounts 연동 검증**

- 프로젝트 루트의 `uploads` 디렉터리를 확인하여 웹 브라우저에서 첨부한 이미지 파일이 호스트 파일 시스템에 저장되었는지 확인.
- 프로젝트 루트의 `logs` 디렉터리를 확인하여 Spring Boot 애플리케이션의 실행 시스템 로그 파일이 호스트 파일 시스템에 정상적으로 기록되고 있는지 확인.

### **8.4 컨테이너 재시작 및 데이터 지속성(DB 및 첨부파일) 영속성 검증**

#### **1) 컨테이너 완전 삭제 후 재구동**

- 실행 중인 애플리케이션 및 DB 컨테이너를 강제 정지 후 호스트에서 완전 삭제함.

```bash
# 15. 실행 중인 컨테이너 정지 및 완전히 삭제
docker stop board-app board-db

```

#### **2) 동일한 볼륨 및 바인드 마운트 옵션으로 컨테이너 재구동**

```bash
# 16. DB 컨테이너 재구동 (동일 Named Volume 마운트)
MSYS_NO_PATHCONV=1 docker run -d --name board-db \
  --network board-net \
  -p 3306:3306 \
  -v board-db-data:/var/lib/mysql \
  -e MYSQL_DATABASE=board_db \
  -e MYSQL_USER=board-app \
  -e MYSQL_PASSWORD=Board123! \
  -e MYSQL_ROOT_PASSWORD=rootpass \
  mysql:9.7

# 17. Spring Board 컨테이너 재구동 (동일 Bind Mounts 마운트, 기존 DB 데이터 보존을 위해 -e SPRING_SQL_INIT_MODE=always 환경변수는 제거)
MSYS_NO_PATHCONV=1 docker run -d --name board-app \
  --network board-net \
  -p 80:8080 \
  -v "${PWD}/uploads:/app/uploads" \
  -v "${PWD}/logs:/app/logs" \
  -e SPRING_DATASOURCE_URL="jdbc:mysql://board-db:3306/board_db?useSSL=false&allowPublicKeyRetrieval=true" \
  -e SPRING_DATASOURCE_USERNAME=board-app \
  -e SPRING_DATASOURCE_PASSWORD=Board123! \
  {dockerhub-username}/spring-board:1.0
```

- 웹 브라우저 접속(`http://localhost`)을 통해 컨테이너 삭제 전 등록해둔 DB 게시글 데이터 및 호스트 `uploads` 디렉터리의 첨부파일이 손실 없이 온전하게 유지 및 조회되는지 최종 검증.
