## 3. Docker 네트워크 드라이버 운용 (bridge, host, overlay)

- Docker 네트워크는 컨테이너 간 통신 및 호스트 외부 통신망 격리를 제어하는 핵심 서브시스템

### 3.1 Bridge Network (기본 및 사용자 정의 브릿지)

- 단일 호스트 내부에서 컨테이너 간 가상 사설 네트워크 격리 환경을 형성함

**1) 기본 브릿지 (bridge)**

- 컨테이너 생성 시 네트워크를 지정하지 않으면 기본 할당되며, 컨테이너 IP 주소를 통해서만 상호 통신이 가능함

**2) 사용자 정의 브릿지 (User-defined Bridge)**

- 사용자가 직접 생성한 브리지 네트워크
- IP 주소뿐만 아니라 컨테이너 이름(Container Name)을 기반으로 자동 DNS 이름 풀이(Name Resolution)를 제공함
- `docker network create [네트워크명]` 명령어를 사용하여 독립된 사용자 정의 브릿지 네트워크를 사전에 생성
- 동작 원리: Docker 엔진이 내장 DNS 서버(127.0.0.1)를 구동하여 컨테이너 내부에 자동 등록하고, 컨테이너 이름을 가상 IP 주소로 동적 매핑함
- 동일한 사용자 정의 브릿지에 속한 컨테이너들은 컨테이너 이름으로 서로를 식별하고 통신할 수 있어 Backend - DB 연동에 필수적

```bash
# 1. 사용자 정의 브리지 네트워크 생성
docker network create myapp-net

# 2. 사용자 정의 브리지에 백엔드 DB 컨테이너 연결 구동
docker run -d --name db-server --network myapp-net -p 3306:3306 -e MYSQL_ROOT_PASSWORD=root mysql:9.7

# 3. 동일한 브리지에 웹 애플리케이션 컨테이너 구동 후 컨테이너 이름(db-server)으로 연동
docker run -d --name web-app -p 8080:8080 --network myapp-net eclipse-temurin:25-jre-alpine
```

### 3.2 Host Network

- 컨테이너의 네트워크 격리(Network Namespace)를 제거하고 호스트의 네트워크 인터페이스를 직접 공유하여 사용하는 방식
- 별도의 포트 바인딩 옵션(`-p`)이 필요 없으며, 컨테이너 프로세스가 호스트의 포트를 직접 공유함
- 가상 브리지 조작 및 NAT 변환 과정이 생략되므로 네트워크 I/O 성능 오버헤드가 최소화됨
    - 호스트 상의 기존 포트 사용 현황과 충돌가능성 및 macOS/Windows 가상화 환경에서의 작동 제약이 존재하므로 주의가 필요
- Host Network는 극단적인 네트워크 I/O 성능 극대화가 필요한 예외적인 케이스로 한정하여 활용
    - 대부분의 경우 보안 격리와 포트 관리가 용이한 Bridge Network가 표준으로 사용되며,

```bash
# 호스트 네트워크 모드로 웹 서버 구동 (호스트 80 포트를 직접 점유)
docker run -d --name host-web --network host nginx:alpine
```

### 3.3 Overlay Network

- 서로 다른 물리 서버(또는 VM 노드)에 존재하는 컨테이너들을 단일 가상 사설 네트워크 서브넷으로 연결하는 분산 네트워크 드라이버
- Docker Swarm 또는 쿠버네티스(Kubernetes) 환경에서 다중 노드 간 컨테이너 분산 통신을 구축할 때 활용됨
- VXLAN(Virtual Extensible LAN) 캡슐화 기술을 바탕을 암호화된 터널링 통신을 지원

```bash
# Docker Swarm 클러스터 초기화 후 오버레이 네트워크 생성 예시
docker swarm init
docker network create -d overlay --attachable my-overlay-net
```

### **3.4 Docker 네트워크 주요 CLI 명령어**

#### **1) `docker network ls`**

```bash
docker network ls
```

- 호스트 내에 존재하는 Docker 네트워크 목록(bridge, host, none 등)을 조회함.

#### **2) `docker network inspect [네트워크명]`**

```bash
docker network inspect myapp-net
```

- 특정 네트워크의 상세 가상 서브넷 정보 및 연결된 컨테이너 IP 주소를 확인함.

#### **3) `docker network connect [옵션] [네트워크명] [컨테이너명]`**

```bash
docker network connect myapp-net sample-web
```

- 실행 중인 컨테이너를 지정한 네트워크에 추가로 연결함.

#### **4) `docker network prune [옵션]`**

```bash
# 1. 기본 정리 (삭제 여부 확인 프롬프트 후 정리)
docker network prune

# 2. 강제 정리 옵션 적용 (-f 옵션으로 확인 절차 없이 즉시 일괄 정리)
docker network prune -f
```

- 현재 연결된 컨테이너가 없는 고립된 네트워크를 일괄 삭제 및 정리함.
- 주요 옵션
    - `f` (`-force`): 별도의 삭제 승인 확인 절차 없이 즉시 강제로 정리함.

## 4. 데이터 지속성 통제 (Bind Mounts VS Named Volumes)

- 컨테이너 내부 쓰기 레이어는 컨테이너 정지 및 삭제 시 데이터가 소멸되므로, 영구 보존이 필요한 데이터를 위해 데이터 지속성(Data Persistence) 메커니즘을 사용함

### 4.1 Named Volumes

**1) Named Volumes 작동 원리 및 특징**

- Docker 데몬이 직접 관리하는 전용 영역(`/var/lib/docker/volumes/`)에 독립된 데이터 볼륨을 생성하고 컨테이너와 연동하는 방식
- 호스트의 디렉토리 구조에 의존하지 않으며 복수 컨테이너 간 데이터 공유 및 데이터베이스 파일 영구 보존에 적합함

**2) 볼륨 관리 CLI 명령어 (`docker volume`)**

```bash
# 1. DB 데이터 전용 볼륨 생성 및 마운트 구동
docker volume create dbdata
docker run -d --name db-server --network myapp-net -p 3306:3306 -v dbdata:/var/lib/mysql -e MYSQL_ROOT_PASSWORD=secret mysql:9.7

# 2. 볼륨 목록 조회 및 상세 정보 확인
docker volume ls
docker volume inspect dbdata
```

- `docker volueme create [볼륨명]`: 독립된 데이터 볼륨을 새로 생성함
- `docker volume ls`: 호스트 내에 생성된 볼륨 목록을 조회함
- `docker volume inspect [볼륨명]`: 특정 볼륨을 상세 저장 경로 및 정보를 확인함
- `docker volume rm [볼륨명]`: 사용하지 않는 볼륨을 삭제함

### 4.2 Bind Mounts

**1) Bind Mounts 작동 원리 및 특징**

- 호스트 파일 시스템의 특정 절대 경로(Absolute Path)를 컨테이너 내부 디렉토리 경로와 1대1로 직접 마운트하여 공유하는 메커니즘)
- 호스트의 외부 설정 파일 (application.yml)이나 로그, 첨부 파일 디렉토리를 이미지를 재빌드하지 않고 컨테이너 내부 환경에 실시간으로 반영 및 보존함
- 로컬 개발 환경에서 Hot Reloding, 웹 정적 리소스 테스트, 외부 설정 파일 주입 시 유용함

**2) 마운트 읽기 전용 보안 옵션 (`:ro`)**

- 마운트 옵션 뒤에 `:ro` (read-only)를 붙여 컨테이너 내부에서 호스트 파일 시스템의 훼손을 방지하는 읽기 전용 보안 권한을 부여할 수 있음

```bash
# 1. 호스트 디렉터리 생성 및 설정 파일 준비
mkdir -p ./config ./logs ./uploads
echo "server.port=8080" > ./config/application-prod.yml

# 2. 읽기 전용 보안 옵션(:ro)과 함께 바인드 마운트 구동
docker run -d --name spring-board-app -p 8080:8080 \
  -v $(pwd)/config/application-prod.yml:/app/config/application-prod.yml:ro \
  -v $(pwd)/logs:/app/logs \
  -v $(pwd)/uploads:/app/uploads \
  spring-board:1.0
```

# Spring Board 컨테이너 배포 및 구동 실습

- 사용자 정의 Bridge 네트워크를 구축하고, 백엔드 DB 컨테이너(`board-db`)와 Spring Boot 기반 게시판 애플리케이션 컨테이너(`spring-board`)를 연동하여 배포하는 프로세스 실습

## **1. 실습 인프라 구성 및 네트워크 선언**

- 독립된 서브넷 통신망 형성을 위해 `board-net` 전용 브리지 네트워크를 생성함.

```bash
# 1. Spring Board 애플리케이션 전용 사용자 정의 네트워크 생성
docker network create board-net
```

## **2. MySQL 데이터베이스 컨테이너 구동**

- 백엔드 데이터 저장소인 MySQL 9.7 컨테이너를 생성하여 `board-net` 네트워크에 연동함.

```bash
# 2. MySQL DB 컨테이너 백그라운드 구동 및 환경 변수 설정
docker run -d --name board-db \
  --network board-net \
  -e MYSQL_DATABASE=board_db \
  -e MYSQL_USER=boarduser \
  -e MYSQL_PASSWORD=boardpass \
  -e MYSQL_ROOT_PASSWORD=rootpass \
  -p 3306:3306 \
  mysql:9.7
```

## **3. Spring Board 이미지 빌드 및 Docker Hub 배포**

- Gradle의 `bootBuildImage` 기능을 활용하여 Spring Boot 애플리케이션 이미지를 빌드하고 Docker Hub 레지스트리에 배포.

```bash
# 3. bootBuildImage를 활용한 OCI 컨테이너 이미지 빌드 (Docker Hub 사용자명/이미지명:태그 지정)
./gradlew bootBuildImage --imageName={dockerhub-username}/spring-board:1.0

# 4. Docker Hub 인증 로그인
docker login

# 5. 빌드된 이미지를 Docker Hub 원격 레지스트리에 업로드
docker push {dockerhub-username}/spring-board:1.0
```

## **4. Spring Board 애플리케이션 컨테이너 배포**

- 게시판 컨테이너 이미지를 다운로드하여 DB 컨테이너 이름(`board-db`)을 호스트명으로 자동 연동함.

```bash
# 6. Docker Hub에서 이미지를 가져와 Spring Board 애플리케이션 컨테이너 배포 및 포트 바인딩(80:8080)
docker run -d --name spring-board \
  --network board-net \
  -p 80:8080 \
  -e SPRING_DATASOURCE_URL="jdbc:mysql://board-db:3306/board_db?useSSL=false&allowPublicKeyRetrieval=true" \
  -e SPRING_DATASOURCE_USERNAME=boarduser \
  -e SPRING_DATASOURCE_PASSWORD=boardpass \
  kilyong/spring-board:1.0
```

## **5. 배포 상태 검증 및 로그 모니터링**

- 컨테이너의 정상 실행 상태와 Spring Boot 웹 애플리케이션 구동 로그를 모니터링함.

```bash
# 7. 실행 중인 컨테이너 상태 및 포트 매핑 확인
docker ps

# 8. Spring Board 컨테이너 초기화 로그 실시간 모니터링
docker logs -f spring-board
```
