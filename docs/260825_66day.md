## 1. Nginx 리버스 프록시 연동 및 다중 컨테이너 환경 구축

- 앞단에 Nginx 웹 서버를 리버스 프록시 및 로드 밸런서로 배치하고, 뒷단에 복수의 Spring Board 애플리케이션 컨테이너를 띄워 부하 분산 및 무중단 배포 실습 환경을 구축함
- Nginx
    - 동시 트래픽 처리에 특화된 고성능 오픈소스 웹 서버
    - 최앞단에서 클라이언트 요청을 중계 및 분산하는 대표적인 리버스 프록시 및 로드 밸런싱 소프트웨어 엔진
    - Nginx 공식 문서: https://nginx.org/en/docs/
    - Nginx 공식 한글 문서 (NGINX Store): https://nginxstore.com/blog/nginx/

## 2. Nginx 리버스 프록시 아키텍처 및 로드 밸런싱 원리

### 2.1 리버스 프록시 및 로드 밸런싱 핵심 개념

- 리버스 프록시(Reverse Proxy) 역할
    - 클라이언트의 모든 HTTP 요청(80 포트)을 최앞단에서 수신한 후, 내부 가상 사설 네트워크(`board-net`)에 존재하는 복수의 애플리케이션 컨테이너로 요청을 안전하게 중계 전달함
- 로드 밸런싱 및 고가용성 보장
    - 라운드 로빈(Round Robin) 알고리즘을 기반으로 트래픽을 각 컨테이너로 균등하게 분산
    - 장애가 발생한 인스턴스를 자동으로 검출하여 정상 인스턴스로 요청을 우회함

### 2.2 Nginx 기반 다중 컨테이너 구동의 핵심 이점

- 무중단 배포 (Zero-Bowntime Deployment)
    - 신규 버전 배포 시 특정 애플리케이션 컨테이너를 정지하고 업데이트하는 동안, Nginx가 트래픽을 정상 구동 중인 타 컨테이너로 유연하게 중계 전달하여 사용자 서비스 중단 없는 롤링 배포(Rolling Update)를 달성함
- 프로세스 수준의 장애 격리 및 자동 우회 (Failover)
    - 특정 애플리케이션 인스턴스에서 메모리 누수나 JVM Crash 장애가 발생하더라도, Nginx가 정상 컨테이너로요청을 즉시 우회시켜 전체 시스템 셧다운을 방지함
- JVM GC(Garbage Collection) 정지 시간 단축 및 자원 효율화
    - 초대형 단일 JVM 프로세스보다 적정 크기의 다중 JVM 컨테이너로 분산 구동함으로써 Garbage Collection에 의한 Stop-The-World 일시 정지 여파를 줄이고 멀티코어 CPU자원 활용도 극대화함.
- 클라우드 및 MSA 아키텍처 이관 사전 검증
    - 세션 정합성(Stateless, Token, Redis 세션 등) 및 로드 밸런싱 환경을 단일 호스트 상에서 따라 미리 구축하여 다중 노드 클라우드 환경으로 이식을 사전 검증

## **3. Nginx 설정 파일(nginx.conf) 작성 및 업스트림 선언**

- 프로젝트 루트에 Nginx 설정 파일(`nginx.conf`)을 작성하여 `upstream` 블록에 다중 Spring Board 컨테이너 서비스명을 선언함.

```
events { worker_connections 1024; }

http {
    upstream backend-board {
        server board-app-1:8080;
        server board-app-2:8080;
    }

    server {
        listen 80;

        location / {
            proxy_pass http://backend-board;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        }
    }
}
```

- Nginx 설정 파일(`nginx.conf`) 핵심 구성 항목
    - `events { worker_connections 1024; }`: Nginx의 비동기 이벤트 처리 구조를 정의하는 컨텍스트 블록으로, 하나의 워커 프로세스(보통 호스트의 CPU 코어 개수만큼 생성됨)가 동시에 처리할 수 있는 최대 클라이언트 커넥션 수(1024개)를 지정함.
    - `http`: HTTP 웹 프로토콜 관련 전반적인 서버 설정(로드 밸런싱, 프록시 전달, HTTP 헤더 제어 등)을 총괄하는 최상위 컨텍스트 블록.
    - `upstream backend-board`: 백엔드로 트래픽을 중계 전달할 애플리케이션 컨테이너 그룹(로드 밸런싱 대상 서버 묶음)을 정의하는 블록으로, 도커 내장 DNS 서비스를 활용하여 동일 브릿지 네트워크(`board-net`) 상의 컨테이너 서비스명(`board-app-1:8080`, `board-app-2:8080`)을 직접 지정함.
    - `server`: 외부 클라이언트의 접속 요청을 수신하고 분산 처리 방식을 결정하는 가상 호스트(Virtual Host) 서버 설정 블록.
    - `listen 80`: Nginx 최앞단 프록시 서버가 외부 클라이언트로부터 HTTP 네트워크 요청을 수신할 수신 포트(80번 포트)를 지정함.
    - `location /`: 요청된 URL 경로의 루트(`/`) 이하 모든 HTTP 요청을 감지하여 내부 블록에 정의된 프록시 전달 규칙을 실행함.
    - `proxy_pass http://backend-board`: 수신된 모든 클라이언트 HTTP 요청을 앞서 `upstream`에 선언된 `backend-board` 애플리케이션 서버 그룹으로 중계 및 부하 분산 전달.
    - `proxy_set_header`
        - 요청을 백엔드 애플리케이션 컨테이너로 전달할 때 클라이언트의 실제 원본 요청 헤더 정보를 유실 없이 보존하여 전송하기 위한 설정 지시어.
        - `Host $host`: 클라이언트가 요청 시 사용한 원본 호스트 도메인 또는 IP 주소 정보를 보존하여 전송함.
        - `X-Real-IP $remote_addr`: Nginx 프록시를 거치기 전 실제 클라이언트의 원본 IP 주소를 보존하여 전송함.
        - `X-Forwarded-For $proxy_add_x_forwarded_for`: 거쳐온 모든 프록시 서버의 IP 주소 이력(Chain)을 덧붙여 백엔드 서비스로 전달함.

```java
    private void logProxyHeaders(HttpServletRequest request) {

        // Nginx 프록시 요청 헤더 로그 출력 메서드 호출
```

## **5. Nginx 및 다중 Spring Board 컨테이너 연동 배포**

- 동일한 `board-net` 사용자 정의 브릿지 네트워크 상에 백엔드 DB, Nginx 요청 헤더 로그 코드가 포함된 복수의 Spring Board 컨테이너(board-app-1, board-app-2), 그리고 앞단의 Nginx 컨테이너를 구동함.
- 컨테이너별 독립 로그 파일명 지정 (`e LOGGING_FILE_NAME`): 동일한 호스트 디렉터리(`logs`)를 공용 마운트할 때 발생할 수 있는 파일 I/O 락(Lock) 경합 및 로그 텍스트 얽힘(Interleaving) 현상을 방지하기 위해, 각 컨테이너 구동 시 독립된 로그 파일명(`board-app-1.log`, `board-app-2.log`)을 환경 변수로 전달하여 기록함.

```bash

MSYS_NO_PATHCONV=1 docker run -d --name board-app-1 \
  --network board-net \
  -v "${PWD}/uploads:/app/uploads" \
  -v "${PWD}/logs:/app/logs" \
  -e SPRING_DATASOURCE_URL="jdbc:mysql://board-db:3306/board_db?useSSL=false&allowPublicKeyRetrieval=true" \
  -e SPRING_DATASOURCE_USERNAME=board-app \
  -e SPRING_DATASOURCE_PASSWORD=Board123! \
  -e LOGGING_FILE_NAME=/app/logs/board-app-1.log \
  {dockerhub-username}/spring-board:1.1

MSYS_NO_PATHCONV=1 docker run -d --name board-app-2 \
  --network board-net \
  -v "${PWD}/uploads:/app/uploads" \
  -v "${PWD}/logs:/app/logs" \
  -e SPRING_DATASOURCE_URL="jdbc:mysql://board-db:3306/board_db?useSSL=false&allowPublicKeyRetrieval=true" \
  -e SPRING_DATASOURCE_USERNAME=board-app \
  -e SPRING_DATASOURCE_PASSWORD=Board123! \
  -e LOGGING_FILE_NAME=/app/logs/board-app-2.log \
  {dockerhub-username}/spring-board:1.1

# 5. Nginx 설정 파일 바인드 마운트 및 최앞단 웹 서버 컨테이너 구동 (호스트 80 포트 바인딩)
```

# 클라우드 인프라 연동 및 마이크로서비스 아키텍처 확장

- 현대 클라우드 인프라 환경에서는 대규모 소프트웨어 시스템의 변경 이식성과 빠른 배포 속도를 달성하기 위해 마이크로서비스 아키텍처(MSA)와 컨테이너 기술을 결합하여 활용함

## 1. 마이크로서비스 아키텍처(MSA) 개념 및 구조

### 1.1 모놀리식(Monolithic) vs 마이크로서비스(MSA) 비교

- 모놀리식 아키텍처 (Monolithic Architecture)
    - 애플리케이션의 모든 기능(인증, 주문, 결제, 알림 등)이 단일 코드베이스 및 단일 실행 파일 형태로 통합되어 구동되는 구조
    - 시스템 초기 개발은 용이, 서비스 규모가 확장될수록 일부분의 변경 사항으로 인해 전체 애플리케이션을 다시 빌드하고 재배포해야 하는 부담이 발생
    - 특정 모듈의 장애가 시스템 전체 장애로 확산되는 위험이 존재
- 마이크로서비스 아키텍처(Microservices Architecture, MSA)
    - 하나의 대형 애플리케이션을 독립적으로 구동되는 소규모 서비스 단위로 분할하여 구축하는 시스템 아키텍처
    - 각 서비스는 명확한 비즈니스 경계(Bound Context)를 가지며, REST API또는 메세지 큐(Message Queue) 기반의 가벼운 네트워크 프로토콜로 상호 통신함

### 1.2 마이스로서비스의 핵심 설계 특징

- 데이터베이스 격리 (Database per Service)
    - 각 마이크로서비스는 자신만의 전용 DB를 보유하여 서비스 간 데이터 종속성을 완전히 분리함
- 폴리글랏(Polyglot) 구정
    - 서비스별 특성에 맞춰 최적의 언어, 프레임워크 및 데이터베이스(예: Java/Spring, Node.js, Python, Redis 등)를 독립적으로 선택하여 도입할 수 있음
- 독립적 생성 및 라이프사이클 통제
    - 특정 서비스의 배포나 변경 작업이 다른 서비스의 운용에 영향을 주지 않음

## 2. 마이크로서비스 배포 단위로서의 컨테이너 역할

### 2.1 환경 격리 및 배포 이식성 확보

- 복수의 마이크로서비스가 요구하는 각기 다른 실행 런타임, 시스템 라이브러리 및 환경 변수를 컨테이너 이미지 단위로 완전 격리하여 환경 충돌을 방지함
- 로컬 개발 환경, QA 검증 환경, AWS 클라우드 운영 환경 간 완벅한 이식성을 제공함

### 2.2 장애 격리 (Fault Isolation) 및 독립 배포성 보장

- 개별 컨테이너 서비스 내부에서 메모리 누수나 예외 장애가 발생하더라도 타 마이크로서비스 컨테이너가 장애가 전파되지 않음
- 장애가 발생한 특정 서비스 컨테이너만 손쉽게 재시작하거나 이전 정상 버전으로 롤백(Rollback)을 수행할 수 있음

### 2.3 수평적 자동 확장 (Scale-out) 효율성 증대

- 시스템 전체 인프라를 증설할 필요 없이, 트래픽이 폭증한 특정 마이크로서비스(예: 이벤트 기간의 주문/결제 서비스) 컨테이너 인스턴스만 핀포인트로 복제 증설하여 자원 활용률을 극대화함

## 3. 컨테이너 오케스트레이션 생태계 개요

### 3.1 컨테이너 오케스트레이션 (Container Orchestration)개념 및 정의

- 수십 ~ 수천 개에 달하는 수많은 컨테이너의 자동 배치, 스케줄링, 배포, 네트워크 생성, 부하 분산, 상태 감지 및 장애 복구(Self-healing) 등 컨테이너 전체 라이프사이클을 자동화하여 관리하는 원리 및 시스템을 의미
- 오케스트라 지휘자(Orchestrator)가 여러 악기의 연주를 조율하듯, 오케스트레이션 엔진은 클러스터 내 여러 호스트 서버에 분산된 컨테이터들의 자원 할당과 실행 상태를 일관되게 총괄 제어함

### 3.2 컨테이너 오케스트레이션의 필요성

- 수백 ~ 수천 개의 컨테이너가 수십 대의 노드 서버에 분산 운용될 경우, 자동 배치(Scheduling), 상태 감지(Self-healing), 롤링 배포, 로드 밸런싱을 수동으로 관리하기 불가능함
- 서버 장애 발생 시 컨테이너 자동 재배치, 트래픽 급증 시 수평적 자동 확장(Autoscaling), 무중단 업데이트 등 고가용성(HA) 환경을 보장하기 위해 필수적

### 3.3 주요 오케스트레이션 툴 및 AWS 관리형 서비

- Docker Swarm: Docker 엔진에 기본 내장되어 별도의 외부 툴 설치 없이 다중 호스트 클러스터링 환경을 구축할 수 있는 경량 오케스트레이션 툴.
- Kubernetes (k8s): 대규모 컨테이너 자동화 배포, 스케줄링 및 관리를 위한 세계 표준 오픈소스 오케스트레이션 플랫폼.
- Amazon ECS (Elastic Container Service): AWS 인프라 환경과 강력히 통합된 관리형 컨테이너 오케스트레이션 서비스.
- Amazon EKS (Elastic Kubernetes Service): AWS 표준 인프라 상에서 순수 쿠버네티스 컨트롤 플레인을 완전 관리형으로 제공하는 서비스.
- AWS Fargate: 서버 인스턴스(EC2) 프로비저닝이나 관리 부담 없이 컨테이너 단위로만 자원을 할당받아 실행하는 서버리스 20 (Serverless) 컨테이너 컴퓨팅 엔진.

# Dockerfile 개요

## 1. Dockerfile 개념 및 도입 배경

### 1.1 Dockerfile

- 애플리케이션을 컨테이너화하는 데 필요한 베이스 이미지 지정, 런타임 종속성 설치, 소스코드 파일 복사, 환경 변수 선언, 구동 명령 등을 텍스트 형식으로 명시한 자동화 빌드 명세서
- docker build 명령어를 수행하면 Docker Daemon이 Dockerfile에 정의된 명령 지시어를 위에서 아래로 순차 해석하여 컨테이너 이미지를 생성함

```docker
# 1. 베이스 이미지 지정 (Alpine Linux 3.24.1)
FROM alpine:3.24.1

# 2. 컨테이너 내부 작업 디렉터리 설정
WORKDIR /app

# 3. 런타임 환경 변수 선언
ENV APP_ENV=production

# 4. 웹 서버(Nginx) 패키지 설치 및 파일 복사(https://pkgs.alpinelinux.org/packages 에서 패키지 버전 확인)
RUN apk update && apk add --no-cache nginx=1.31.4
COPY index.html /usr/share/nginx/html/index.html

# 5. 수신 포트 명세 및 포그라운드 구동 명령 지정
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

### 1.2 인프라 구축 방식의 패러다임 전환

- 전통적 수동 구축 방식
    - 시스템 관리자가 서버 OS에 직접 접속하여 쉘 스크립트 실행이나 패키지 명령을 수동으로 실행
    - 이로 인해 작업자 간 설정 오차, 환경 문서화 누락, 런타임 버전 파편화 및 불일치 문제 발생
- Dockerfile 기반 자동화 방식
    - 인프라 구성을 코드로 명시하는 코드로서의 인프라(IaC, Infrastructure as Code) 개념을 실현함
    - 인프라 명세 자체가 버전 관리 시스템(Git 등)에 의해 관리되므로 환경 구축 과정이 동일하게 재현됨
