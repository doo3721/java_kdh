# 가상화 기술 및 Docker 기본 원리

## 1. 서버 가상화 발전 과정 및 필요성

- 온프레미스 인프라 환경에서 단일 서버에 하나의 운영체제와 단일 애플리케이션을 구동할 경우 시스템 자원 활용률이 크게 저하되는 비효율이 발생
- 물리 서버 자원의 효율적 분배와 종속성 격리를 달성하기 위해 가상화 기술을 도입

## 2. 가상 머신과 컨테이너 가상화 구조 비교

- 단일 물리 서버 환경에서 복수의 애플리케이션을 직접 구동할 경우, 공유 시스템 라이브러리 패키지의 버전 충돌이 발생하고 특정 프로세스의 호스트 자원 독점으로 인해 전체 시스템 안정성이 저해되는 한계가 존재
- 이러한 물리 인프라 자원의 격리 한계와 환경 이식성 문제를 해결하고 독립적인 애플리케이션 구동 환경을 제공하기 위해 가상화 기술을 활용함

### 2.1 가상 머신 가상화 구조

- 물리적 하드웨어 상위에 하이퍼바이저를 두고, 그 위에 독립된 게스트 운영체제를 각각 설치하여 애플리케이션을 실행하는 구조, AWS EC2 인스턴스가 대표적인 VM 방식의 가상화 환경
- 각 VM마다 별도이 OS 커널(Kernel), 바이너리, 시스템 라이브러리가 포함되므로 디스크 용량이 대용량(수 GB ~ 수십 GB)이며 부팅 시간이 수 분 소요됨
- 하드웨어 자원 에뮬레이션 처리로 인해 CPU 및 메모리 성는 오버헤드가 발생

### 2.2 컨테이너 가상화 구조

- 컨테이너 가상화는 호스트 운영체제(Host OS)의 커널을 공유하면서, 별도의 게스트 OS 없이 프로세스 수준에서 애플리케이션 실행 환경을 격리하여 구동하는 방식
- 게스트 OS가 존재하지 않으므로 이미지 크기가 작고(수 MB ~ 수백 MB), 부팅 시간이 수 초 이내로 신속함
- 커널 직접 호출 방식을 사용하므로 하이퍼바이저 오버헤드가 제거되어 베어메탈(Bare-metal)에 근접한 실행 성능을 확보함

## 3. Docker 플랫폼 개요 및 기술적 의의

### 3.1 Docker 플랫폼 정의

- 2013년 dotCloud(현 Docker Inc.)에서 오픈소스로 공개한 컨테이너 기반 가상화 플랫폼
- 리눅스 커널의 자원 격리 기술(cgroups, namespaces)을 바탕으로 애플리케이션을 경량화된 컨테이너 이미지 형태로 패키징하여 배포 및 구동하도록 지원함

### 3.2 소프트웨어 공급망(Software Supply Chain)의 혁신

- 소스 코드 작성 → 컨테이너 이미지 빌드 → 중앙 레지스트리 저장 → 운영 서버 배포로 이어지는 자동화된 CI/CD (Continuous Integration / Continuous Deployment) 파이프라인의 핵심 기본 실행 단위로 정착함
- 로컬 개발 환경과 검증/운영 환경 간 배포 이식성을 제공하여 소프트웨어 배포 주기를 단축함

# **Docker 설치 및 실행 환경 구축**

- 참고: https://www.docker.com/products/docker-desktop/

## **1. Docker Desktop 개요**

- Docker Desktop은 Windows, macOS 환경에서 리눅스 컨테이너 개발 및 실행 환경을 통합 관리하기 위한 데스크톱 애플리케이션.
- Docker Engine, Docker Client, Docker Compose 등 주요 컨테이너 관리 인터페이스를 단일 패키지로 제공함.

## **2. Windows 환경**

### **2.1 WSL (Windows Subsystem for Linux) 2**

- Docker Desktop은 Windows 환경에서 리눅스 커널 기반 컨테이너를 구동하기 위한 핵심 백엔드로 WSL 2 엔진을 활용함.
- Docker Desktop 설치 및 구동 전 Windows 가상화 기능인 WSL 2를 사전에 활성화하고 설치해야 함.
- PowerShell(관리자 권한)에서 `wsl --install` 명령을 실행하여 WSL 2 환경을 구축.

### **2.2 Docker Desktop 설치 파일 다운로드 및 실행**

- Docker 공식 웹사이트에서 `Docker Desktop for Windows - x86_64` 버튼을 클릭하여 설치 파일을 다운로드.

### **2.3 WSL 2 백엔드 연동 옵션 선택**

- 설치 진행 중 Use WSL 2 instead of Hyper-V 옵션을 선택하여 Docker 데몬이 WSL 2 엔진을 백엔드로 연동하도록 설정.

### **2.4 시스템 재부팅 및 구동 확인**

- 시스템 재부팅 후 Docker Desktop을 구동하여 상태 표시줄에서 정상 작동 메시지를 확인.

## **3. macOS 환경**

### **3.1 아키텍처별 설치 파일 선택 및 다운로드**

- Docker 공식 웹사이트에서 칩셋 아키텍처에 맞는 설치 파일을 다운로드.
- Apple Silicon (M1/M2/M3/M4) 칩셋 환경은 `Docker Desktop for Mac with Apple Silicon` 선택해서 다운로드.
- Intel 칩셋 환경은 `Docker Desktop for Mac with Intel chip` 선택해서 다운로드.

### **3.2 애플리케이션 설치 및 등록**

- 다운로드된 `.dmg` 파일을 실행하여 `Docker.app` 아이콘을 `Applications` (응용 프로그램) 폴더로 드래그 앤 드롭함.

### **3.3 가상화 엔진 및 리소스 할당 설정**

- Docker Desktop 실행 후 Settings -> General 메뉴에서 Use Virtualization framework 옵션을 선택.
- Resources 메뉴에서 CPU 및 Memory 할당량을 환경에 맞추어 설정함.

### **3.4 시스템 구동 및 정상 작동 확인**

- macOS 상단 메뉴 바에서 Docker 데몬 아이콘이 정상 상태로 활성화되었는지 확인함.

## **4. Linux(Ubuntu) 환경 Docker Engine 설치 및 데몬 설정**

- 리눅스 환경에서는 서버 운영체제 상에 공식 패키지 리포지토리 7를 등록하고 Docker Engine 데몬 패키지를 직접 설치하여 운용함.

### **4.1 구버전 패키지 정리 및 필수 패키지 설치**

```bash
# 충돌을 방지하기 위한 기존 구버전 패키지 제거
sudo apt-get remove docker docker-engine docker.io containerd runc

# 패키지 목록 업데이트 및 HTTPS 통신용 필수 패키지 설치
sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg lsb-release
```

### **4.2 Docker 공식 GPG 키 및 보안 리포지토리 등록**

```bash
# Docker 공식 GPG 키 다운로드 및 저장
sudo mkdir -p /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg

# 검증된 안정판(stable) 리포지토리 등록
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu \
  $(lsb_release -cs) stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
```

### **4.3 Docker Engine 패키지 설치 및 데몬 활성화**

```bash
# APT 리포지토리 갱신 후 최신 Docker Engine 패키지 설치
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

# Docker 데몬 자동 시작 설정 및 정상 작동 상태 확인
sudo systemctl enable --now docker
sudo systemctl status docker
```

## **5. 설치 상태 검증 및 non-root 권한 설정**

- Linux 환경에서 기본 설치 상태에서는 `sudo` 권한을 가진 사용자만 Docker 데몬 Unix 소켓 8에 접근 가능하므로, 일반 사용자 계정을 `docker` 그룹에 포함시켜 보안 권한을 적용함.

### **5.1 사용자 권한 부여 및 시스템 적용**

```bash
# 현재 사용자 계정을 docker 그룹에 추가하여 sudo 없이 실행 허용
sudo usermod -aG docker $USER

# 그룹 변경 사항을 현재 쉘 세션에 즉시 적용 (또는 재로그인)
newgrp docker
```

### **5.2 헬로 월드 컨테이너 실행 및 설치 검증**

```bash
# sudo 없이 검증용 헬로 월드 컨테이너 구동
docker run hello-world

# Docker Engine 버전 및 시스템 기본 정보 확인
docker version
docker info
```

# Docker 아키텍처 및 핵심 구성 요소

## 1. Docker Client 및 Daemon

- Docker Daemon (`dockerd`): 호스트 시스템에 상주하며 컨테이너 생성, 실행, 이미지 빌드, 네트워크/볼륨 관리를 총괄 수행하는 백그라운드 프로세스
- Docker Client (`docker`): 사용자가 CLI 명령어를 입력하면 REST API를 통해 Docker Daemon으로 요청을 전달하는 인터페이스 도구

## 2. Docker Image 및 Container

- Docker Image: 컨테이너를 생성하기 위한 읽기 전용 템플릿으로, 애플리케이션 바이너리, 설정 파일, 종속 라이브러리가 레이어 구조로 정적으로 저장
- Docker Container: Docker Image가 실행되어 독립된 메모리와 파일 시스템 공간을 할당받은 런타임 프로세스 실행 상태

## 3. Docker Registry

- 컨테이너 이미지를 저장, 버전 관리 및 공유하기 위한 중앙 저장소 시스템
- 주요 레지스트리 종류
    - Docker Hub: Docker 기본 공용 중앙 저장소 (docker.io), 레지스트리주소 생략시 사용되는 기본값
    - GHCR (Github Container Registry): Github 계정 권한 및 CI/CD 파이프라인과 연동되는 레지스트리 서비스 (ghcr.io)
    - Amazon ECR (Amazon Elastic Container Registry): AWS 클라우드 인프라 기반의 관리형 사설 이미지 저장소 ([aws_account_id].dkr.ecr.[region].amazonaws.com)

# Docker CLI 명령어를 황용한 컨테이너 기초

- Docker CLI(Command Line Interface)는 사용자가 `docker` 명령어와 옵션을 입력하여 Docker 데몬과 통신하고 컨테이너 및 이미지의 상태를 제어하는 핵심 도구

## 1. 이미지 조작 및 레지스트리 연동 CLI 명령어

### 1.1 이미지 검색 및 다운로드

- Docker Hub 웹 검색: 공식 이미지 저장소 사이트(https://hub.docker.com)에서 사용할 소프트웨어를 검색하여 정확한 이미지 명칭과 태그를 확인
- CLI 키워드 검색: `docker search [키워드]` 명령을 통해 터미널에서 즉시 공용 이미지 이름을 확인
- 로컬 이미지 목록 확인: `docker image ls` 명령을 통해 이미 다운로드된 로컬 이미지명을 확인
- 이미지 이름 표기 규칙 (Naming Convention)
    - 표준 형식: `[레지스트리주소]/[소유자명]/이미지명:태그`
    - 공식 이미지 예시: `ubuntu:24.04`, `mysql:9.7` (소유자명이 없는 경우 Docker Hub 공식 검증 이미지)
    - 태그 생략 시 동작: 태그를 명시하지 않고 `docker pull ubuntu`와 같이 실행하면 기본값으로 최신 버전 태그인 `latest` 태그가 적용됨
- `docker search [키워드]`: Docker Hub 중앙 레지스트리에 등록된 공용 이미지 목록을 키워드로 검색함
- `docker pull [이미지명]:[태그]`: 지정한 이미지와 특정 태그(버전)를 로컬 호스트로 다운로드함. 태그 생략시 기본값으로 `latest`태그가 적용됨

```bash
# Docker Hub에서 이미지 검색
docker search ubuntu

# 태그를 지정하여 특정 버전 이미지 다운로드
docker pull ubuntu:26.04
```

### 1.2 로컬 이미지 관리 및 태그 지정

- `docker image ls`: 로컬 저장소에 다운로드되어 있는 Docker 이미지 목록(REPOSITORY, TAG, IMAGE ID, CREATED, SIZE 등)을 조회함
- `docker tag [원본이미지]:[태그] [새이미지]:[새태그]`: 기존 이미지에 새로운 별칭이나 레지스트리 주소가 포함된 라벨 태그를 추가함
- `docker image rm [이미지ID|이미지명]`: 지정한 로컬 이미지를 삭제함
    - 해당 이미지를 사용하는 컨테이너가 존재할 경우 컨테이너를 먼저 삭제해야 함

```bash
# 다운로드된 로컬 이미지 목록 확인
docker image ls

# 이미지 태그(별칭) 추가
docker tag ubuntu:26.04 my-repo/ubuntu:custom

# 필요 없는 로컬 이미지 삭제
docker image rm ubuntu:26.04
```

## 2. 컨테이너 라이프사이클 통제 및 상태 관리 CLI 명령어

### **2.1 컨테이너 생성 및 백그라운드 구동**

- `docker run [옵션] [이미지명]`: 이미지를 기반으로 새로운 컨테이너를 생성하고 시작함 (`docker create` + `docker start` 동작을 결합 수행함).
- 주요 옵션
    - `d` (detach): 컨테이너를 백그라운드 데몬 프로세스로 구동함.
    - `-name [이름]`: 컨테이너에 고유 식별 이름을 부여함.
    - `p [호스트포트]:[컨테이너포트]`: 호스트의 포트와 컨테이너 내부 포트를 연결(포트 바인딩)함.

```bash
# 백그라운드 데몬 형태(-d)로 포트 매핑(-p 80:80) 컨테이너 구동
docker run -d --name my-web -p 80:80 docker/getting-started
```

### **2.2 컨테이너 상태 조회 및 로그 모니터링**

- `docker ps`: 현재 실행 중인 컨테이너 목록(CONTAINER ID, IMAGE, COMMAND, PORTS, NAMES 등)을 조회함.
    - 주요 옵션: `a` (all) 옵션을 추가하면 정지되거나 종료된 컨테이너를 포함한 전체 목록을 출력함.
- `docker logs [컨테이너ID|이름]`: 컨테이너 내부 프로세스가 표준 출력(stdout) 및 표준 에러(stderr)로 내보낸 로그 기록을 확인함.
    - 주요 옵션: `f` (follow) 옵션을 지정하면 로그 출력을 실시간 스트리밍으로 지속 모니터링함.

```bash
# 실행 중인 컨테이너 목록 조회
docker ps

# 정지된 컨테이너를 포함한 전체 목록 조회
docker ps -a

# 컨테이너 실시간 출력을 로그 스트리밍으로 확인
docker logs -f my-web
```

### **2.3 컨테이너 내부 진입 및 인터랙티브 제어**

- `docker exec [옵션] [컨테이너ID|이름] [명령어]`: 실행 중인 컨테이너 내부에서 새로운 명령어를 추가로 수행함.
    - 주요 옵션: `it` (`i` interactive + `t` tty) 옵션을 조합하여 컨테이너 내부의 쉘(/bin/sh 또는 /bin/bash)과 대화형 터미널 통신 세션을 연결함.
- `docker stop [컨테이너ID|이름]`: 실행 중인 컨테이너 프로세스에 정지 신호(SIGTERM)를 전달하여 안전하게 정지시킴.
- `docker rm [컨테이너ID|이름]`: 정지 상태의 컨테이너를 호스트 시스템에서 완전히 삭제함.

```bash
# 실행 중인 컨테이너 내부 대화형 쉘 접속 (Windows 환경에서는 PowerShell 또는 CMD 권장)
docker exec -it my-web /bin/sh

# 컨테이너 프로세스 정지 및 삭제
docker stop my-web
docker rm my-web
```

## 3. 데이터 지속성 통제 (Bind Mounts VS Named Volumes)

- 컨테이너 내부 쓰기 레이어는 컨테이너 정지 및 삭제 시 데이터가 소멸되므로, 영구 보존이 필요한 데이터를 위해 데이터 지속성(Data Persistence) 메커니즘을 사용함

### 3.1 Bind Mounts

- 호스트 파일 시스템의 특정 절대 경로(Absolute Path)를 컨테이너 내부 디렉토리 경로와 1대1로 직접 마운트하여 공유하는 메커니즘)
- 주요 특징 및 이점
    - 호스트 파일 시스템의 소스 코드나 설정 파일을 변경하면 이미지를 재빌드하지 않아도 컨테이너 내부 환경에 실시간으로 반영됨
    - 로컬 개발 환경에서 Hot Reloding, 웹 정적 리소스 테스트, 외부 설정 파일 주입 시 유용함
    - 마운트 옵션 뒤에 `:ro` (read-only)를 붙여 컨테이너 내부에서 호스트 파일 시스템의 훼손을 방지하는 읽기 전용 보안 권한을 부여할 수 있음

```bash
# 1. 호스트 시스템에 실습용 웹 디렉터리 및 index.html 파일 생성
mkdir -p ./html
echo "<h1>Hello Bind Mounts</h1>" > ./html/index.html

# 2. 호스트 절대 경로(pwd)의 ./html 디렉터리를 Nginx 웹 서버 컨테이너와 마운트하여 구동
docker run -d --name web-bind -p 8080:80 -v $(pwd)/html:/usr/share/nginx/html nginx:alpine

# 3. 읽기 전용(:ro) 옵션을 부여하여 안전하게 호스트 디렉터리 마운트
docker run -d --name web-bind-ro -p 8081:80 -v $(pwd)/html:/usr/share/nginx/html:ro nginx:alpine
```

### 3.2 Named Mount

- Docker 데몬이 직접 관리하는 전용 영역(`/var/lib/docker/volumes/`)에 독립된 데이터 볼륨을 생성하고 컨테이너와 연동하는 방식
- 호스트의 디렉토리 구조에 의존하지 않으며 복수 컨테이너 간 데이터 공유 및 데이터베이스 파일 영구 보존에 적합함

```bash
# 볼륨 생성
docker volume create dbdata

# 볼륨 마운트 수행하여 컨테이너 구동
docker run -d --name mysql-db -v dbdata:/var/lib/mysql -e MYSQL_ROOT_PASSWORD=secret mysql:9.7
```

## 4. Docker 네트워크 드라이버 운용 (bridge, host, overlay)

- Docker 네트워크는 컨테이너 간 통신 및 호스트 외부 통신망 격리를 제어하는 핵심 서브시스템

### 4.1 Bridge Network (기본 및 사용자 정의 브릿지)

- 단일 호스트 내부에서 컨테이너 간 가상 사설 네트워크 격리 환경을 형성함
- 기본 브릿지(`bridge`): 컨테이너 생성 시 네트워크를 지정하지 않으면 기본 할당되며, 컨테이너 IP 주소를 통해서만 상호 통신이 가능함
- 사용자 정의 브릿지 (User-defined Bridge)
    - 사용자가 직접 생성한 브리지 네트워크
    - IP 주소뿐만 아니라 컨테이너 이름(Container Name)을 기반으로 자동 DNS 이름 풀이(Name Resolution)를 제공함
    - 동일한 사용자 정의 브릿지에 속한 컨테이너들은 컨테이너 이름으로 서로를 식별하고 통신할 수 있어 Backend - DB 연동에 필수적

```bash
# 1. 사용자 정의 브리지 네트워크 생성
docker network create my-net

# 2. 사용자 정의 브리지에 백엔드 DB 컨테이너 연결 구동
docker run -d --name db-server --network my-net -e MYSQL_ROOT_PASSWORD=secret mysql:9.7

# 3. 동일한 브리지에 웹 애플리케이션 컨테이너 구동 후 컨테이너 이름(db-server)으로 연동
docker run -d --name web-app -p 8080:8080 --network my-net eclipse-temurin:25-jre-alpine
```

### 4.2 Host Network

- 컨테이너의 네트워크 격리(Network Namespace)를 제거하고 호스트의 네트워크 인터페이스를 직접 공유하여 사용하는 방식
- 주요 특징
    - 별도의 포트 바인딩 옵션(`-p`)이 필요 없으며, 컨테이너 프로세스가 호스트의 포트를 직접 공유함
    - 가상 브리지 조작 및 NAT 변환 과정이 생략되므로 네트워크 I/O 성능 오버헤드가 최소화됨
    - 호스트 상의 기존 포트 사용 현황과 중돌할 수 있으므로 포트 관리에 주의해야 함

```bash
# 호스트 네트워크 모드로 웹 서버 구동 (호스트 80 포트를 직접 점유)
docker run -d --name host-web --network host nginx:alpine
```

### 4.3 Overlay Network

- 서로 다른 물리 서버(또는 VM 노드)에 존재하는 컨테이너들을 단일 가상 사설 네트워크 서브넷으로 연결하는 분산 네트워크 드라이버
- 주요 특징
    - Docker Swarm 또는 쿠버네티스(Kubernetes) 환경에서 다중 노드 간 컨테이너 분산 통신을 구축할 때 활용됨
    - VXLAN(Virtual Extensible LAN) 캡슐화 기술을 바탕을 암호화된 터널링 통신을 지원

```bash
# Docker Swarm 클러스터 초기화 후 오버레이 네트워크 생성 예시
docker swarm init
docker network create -d overlay --attachable my-overlay-net
```

### 4.4 Docker 네트워크 주요 CLI 명령어

```bash
# 1. 호스트 내 네트워크 목록 조회 (bridge, host, none 등)
docker network ls

# 2. 특정 네트워크 상세 정보 및 연결된 컨테이너 IP 확인
docker network inspect my-net

# 3. 실행 중인 컨테이너를 기존 네트워크에 추가 연결
docker network connect my-net my-web

# 4. 사용하지 않는 고립된 네트워크 일괄 정리
docker network prune
```
